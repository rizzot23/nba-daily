# 去球吧 · NBA 每日战报流水线

每天北京时间 14:07 起分四档自动拉取当日 NBA 全部比赛结果，生成一份可直接粘贴进公众号编辑器的战报 HTML，外加一篇「今日主打」的单场稿。

账号名：**去球吧**（公众号 + 头条号同名）。

**一天发两处、共三篇：**

| 发在哪 | 发什么 | 位置 |
|---|---|---|
| 公众号 | 完整战报（15 场全展开） | 主条 / 头条位 |
| 公众号 | 今日主打（只讲一场，深读） | 次条 |
| 头条号 | 今日主打（同一场，另一套写法） | 单篇图文 |

公众号一次群发可以带多条图文，主条 + 次条一起推，读者看完战报往下滑就是深读，不用再等第二天。

**能自动的**：拉数据、聚合比分/单节/球队统计/球员数据、算出每场的「数据看点」、选出当天最值得写的一场、排版成图文、给两个平台各出一份写作稿、提交到仓库。
**不能自动的**：公众号群发。个人未认证订阅号没有群发接口权限（调用返回 48001），最后需要在后台点「群发」并用管理员微信扫码。这一步是微信的设计，绕不过去。

---

## 数据源：不需要任何 Key

主数据源用 ESPN 的公开记分板接口，**不用注册、不用申请 Key**：

- `site.api.espn.com/.../scoreboard?dates=YYYYMMDD` → 比分、状态、开球时间、战绩
- `site.api.espn.com/.../summary?event=<id>` → 单节比分、球队统计、每队球员数据

> 早前用的是 balldontlie，它的免费 Key 只开放 `/games` 和 `/teams`，`/stats`（球员数据）返回 401，属付费档。所以改成 ESPN 打主力，balldontlie 只留作比分兜底——配了 `BALLDONTLIE_API_KEY` 才有，没有也能跑。

## 部署三步

### 1. 建仓库并上传

本地已经初始化好 git 仓库（分支 `main`），只差一个远程地址。

1. 在 GitHub 右上角 `+` → `New repository`，填名字（比如 `nba-daily`），**不要勾选** Add a README / .gitignore / license（否则第一次推送会冲突），点 `Create repository`。
2. 进入新仓库后复制页面上的 HTTPS 地址，把下面两行里的 `<你的用户名>` 和 `<仓库名>` 换掉，粘进终端：

```bash
git remote add origin https://github.com/<你的用户名>/<仓库名>.git
git push -u origin main
```

第一次推会弹窗要求登录。GitHub 现在只认 **Personal Access Token（PAT）**，不认账号密码：

1. 打开 `https://github.com/settings/tokens`（或 `Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token (classic)`）。
2. Note 随便填（比如 `nba-daily`），Expiration 选 90 天或长期，权限**只勾第一项 `repo`**，拉到底 Generate token。
3. `ghp_xxx` 那串**只显示一次**，当场复制。弹窗里用户名填 GitHub 用户名，密码栏粘贴这串 token（不是账号密码）。Windows 会存进凭据管理器，以后不用再输。

如果之前存过错误凭据导致反复认证失败：控制面板 → 凭据管理器 → Windows 凭据 → 删掉 `git:https://github.com` 那条，再推一次。
用 Fine-grained token 也行，但要选到这个仓库并给 **Contents: Read and write**，比 classic 麻烦，第一次建议直接用 classic。
**别把 token 写进 remote URL 或任何要提交的文件**——那等于把仓库钥匙公开。

### 2. 手动跑一次（验证链路）

**先改一个设置，否则跑完推不上去**：`Settings → Actions → General → Workflow permissions` → 选 **Read and write permissions** → Save。
新仓库默认是只读的，机器人生成了战报但没权限提交回去，日志会报 403。

然后：仓库页 → `Actions` → 左侧点「**去球吧 每日战报**」→ 右侧 `Run workflow` → 下拉选 `main` → 再点绿色 `Run workflow`。

**不要等第二天 15:23 才算跑通**：定时任务要等到下一个 cron 时间点才会第一次自己触发，先手动跑一次才能当场确认整条链路没断。
（只有 fork 来的仓库才会出现「Workflows aren't being run on this forked repository」的黄色横幅，自己新建的仓库不用管。）

约 1 分钟跑完。点进去能看到「Summary」页里有一份当天摘要（几场、哪场最胶着、明日焦点是谁），
下方 `Artifacts` 里有 `daily-report-N` 可以下载。同时仓库的 `docs/report.html` 会被机器人自动提交一次。

不需要配任何 Secret。

### 3.（可选）开 Pages，手机上也能看

Settings → Pages → Source 选 `Deploy from a branch` → Branch 选 `main`、目录选 `/docs` → Save。

几分钟后访问 `https://<你的用户名>.github.io/<仓库名>/report.html`，手机上就能直接打开。白天没电脑时先用手机看内容，回到电脑前再粘贴排版、点群发——**手机上只能看，发不了完整战报**，原因见下面「每天怎么用」。

### 4.（可选）配微信提醒

去 [sct.ftqq.com](https://sct.ftqq.com) 用微信扫码登录，拿到一个 `SendKey`（免费版每天 5 条，够用）。
然后仓库 `Settings → Secrets and variables → Actions → New repository secret`，名字填 `SC_KEY`，值粘贴 SendKey。

之后每次生成完会往你微信推一条：标题是「NBA 11月2日 · 15 场」，正文是导语 + 三个标签 + 明日焦点 + 「打开战报」链接。
没配这个 secret 就静默跳过，不影响出稿。

如果 Pages 地址不是按 `<用户名>.github.io/<仓库名>` 推出来的（比如绑了自定义域名），再建一个 **Variable**（不是 Secret）叫 `REPORT_URL`，填完整地址即可。

## 公众号联动：能自动到哪一步

**先说结论：到草稿箱为止，而且这一层建议不做。最后一步「群发」永远是人点的。**

### 个人未认证订阅号的接口权限（2025 年 7 月后）

| 能力 | 接口 | 能不能用 |
|---|---|---|
| 获取 access_token | `/cgi-bin/token` | ✅ 要先配 IP 白名单 |
| 正文图片转存 | `media/uploadimg` | ✅ |
| 封面永久素材 | `material/add_material` | ✅ |
| 新建图文草稿 | `draft/add` | ✅ |
| **群发** | `freepublish/submit`、`message/mass/send` | ❌ 返回 `48001` |

「发布」这组权限在 2025 年 7 月被微信回收了，个人主体和企业未认证号都调不了。这不是配置问题，配什么都绕不过去。

### 为什么不能把建草稿放进 GitHub Actions

微信在**取 access_token 那一步**核对请求方的**公网出口 IP**，不在白名单里直接返回 `40164`。

GitHub Actions 的出口是 Azure 的动态地址段，几百个 IP 且共享。全塞进白名单 = 给所有 GitHub 用户开一个能调你公众号的入口。所以想走 API，必须有一台 **IP 固定**的机器（自购云主机，或用 `ssh -D` 借它的出口 IP）。

**算一笔账**：自动化省掉的只是「全选 + 复制 + 粘贴」这一次操作，而公众号编辑器粘贴时会自动上传图片，比 API 一张张传（15 场就是 15 次串行请求）更稳。为约 10 秒的便利换来一台机器和一把 AppSecret，不划算。

### 一条合规红线

2026 年 3 月 27 日微信公众平台新增「**非真人自动化创作行为**」规定：不得用 AI、脚本、接口替代真人完成内容创作和发布，明确点名「靠脚本托管批量连续发布」，违规会限流、删文甚至封号。

同时它也写明「鼓励创作者用工具辅助创作」，反对的是「完全由自动化程序替代真人」。

**所以现在这个结构是安全的**：程序负责抓数据、算标签、画图、排版，导语和标题由人写，群发由人点。如果改成自动建草稿 + 自动群发，就正好落进被点名的那一类。最后一步必须手动，既是权限限制，也是保护。

## 每天怎么用

| 时间 | 做什么 | 谁做 |
|---|---|---|
| 14:07 / 15:23 / 16:51 / 19:37（四档均全终场才出稿） | 自动生成 `docs/report.html`、`docs/feature.md`、`docs/cover.png` | GitHub Actions |
| 任一档跑完 | 微信收到一条摘要（配了 `SC_KEY` 才有，一天可能不止一条） | GitHub Actions |
| 晚上，有电脑时 | 打开 `publish.html` 确认顶部日期是当天，改导语那 120 字 | 你 |
| 紧接着 | 公众号后台建「多图文」：主条粘战报、封面用 `cover.png`；次条按需从 `feature.md` 写 | 你 |
| 发出前 | 核对 14 张走势图、标题摘要、文末免责声明 | 你 |
| 发 | 点「群发」，管理员微信扫码（不是「发布」） | 你 |
| 发完（可选） | 头条号发主打的另一版，标题换措辞 | 你 |

**发布时间不设死钟点**：战报下午生成后一直挂在 Pages 上，不会过期，按你手边有电脑的时段发即可（建议晚上 21:00 后）。原方案定过 17:30 通勤高峰，但白天没电脑，而「全选复制富文本 → 粘进编辑器 → 确认 14 张走势图」这一步手机替不了：手机 App 编辑器是简易版，跨 App 粘贴只剩纯文字；手机浏览器切电脑 UA 虽能登后台，界面错位、还要另一台设备扫码，只够点群发已存好的草稿。**手机用来打开发布台看战报，发布留到电脑前。** 日更号拼的是「今天有没有」，不是几点发。

**发布入口是 `publish.html`**（Pages 地址同 `report.html`，换一下文件名）。它是个静态页，每次打开实时读取同目录的 `latest.json` / `feature.json` / `feature.md` / `report.html`，把主条链接、标题候选、摘要、封面、全部走势图的 https 直链和发布步骤收在一处，**每次生成后自动换内容，链接永久有效**。发之前先确认页顶的比赛日和生成时间是不是当天；不是当天会亮黄色提示，别急着发。

**公众号怎么一次推两条**：群发页选「图文消息」，进去后左上角「+」（新建消息）可以加第二条，最多 8 条。第一条就是主条（信息流里显示大图那条），第二条是次条。两条一起群发，只消耗当天那一次群发机会，不会分开打扰读者。

**头条发的是同一场，但别复制公众号那篇。** 头条的站外去重会判「疑似搬运」，轻则限流重则扣分；而且公众号次条是写给已经关注你的人看的，头条读者是刷到的陌生人，开头差一句就决定了划不划走。`feature.md` 第 6 节把两边的差异列成了表：字数、开头、人称、数据密度、结尾各不相同。

页面所有样式都是内联的，从浏览器全选复制粘贴到公众号编辑器能保留排版，不需要重新调格式。

**导语那一行必须改。** 脚本会自动选出当天最胶着的一场并给出数据依据（例如「交替领先 5 次，打平 4 次，第 4 节还剩 3:59 才把分差拉开到 5 分以上」），但它只负责摆事实，判断和观点得你自己写。下面带方括号的是占位提示，写完记得删掉。

**激烈度怎么算的**：从逐回合数据里取三个量 —— 交替领先与打平次数、第四节内「分差≤5」的净时长、末节最后两分钟的极值分差。三项加权打分，最高的那场打上「今日最胶着」标签。这样算的好处是垃圾时间追分不会被误判成激烈（分差被拉开后的时长不计分）。

**四个标签怎么分的**（每场最多一个，按优先级抢占，判定都基于可复核的数据）：

| 标签 | 判定条件 |
|---|---|
| 今日最胶着 | 激烈度得分最高 |
| 今日最大逆转 | 胜方一度落后 ≥10 分 |
| 今日最功亏一篑 | 一度落后 ≥10 分、末节追到 5 分内、但仍输了 |
| 今日最平淡 | 激烈度最低，且分差上双、末节基本没缠斗过 |

没比赛够格时就不打标签，不会硬凑。

**绝杀 / 准绝杀**是独立于上面四个标签的「事实标记」，会额外压一行深红徽章，所以一场可以同时是「绝杀」+「今日最胶着」。判定方式：

1. 先找**败方最后一次得分**，之后的比赛段才是真正定胜负的时间
2. 这一段里胜方第一次得分，必须把比分从打平或落后变成领先（反超球）——这样就排除了领先时的罚球
3. 那球发生在第四节或加时，且剩余 ≤ 24 秒

剩余 ≤ 1 秒算「绝杀」，1～24 秒算「准绝杀」。第 2 步之所以绕一圈，是因为反超之后对手常常只能犯规，胜方还会靠罚球涨分；如果直接取「全场最后一次进球」，这类真正的好球会被漏掉。

**页面顺序 = 推荐比赛在前，其余按开球时间跟在后面。**

焦点球星下面先是一个「推荐比赛」小标题，紧跟值得看的那些场次的完整卡片，**第一张固定是导语讲的那场**，剩下几张按好看程度排。推荐场次放完之后是「其余 N 场」小标题，里面的卡片严格按开球时间排。

不再单独做一份「其它推荐比赛」的行式清单。清单和卡片讲的是同一件事，同一场比赛在页面上出现两次，读者只会觉得你在凑篇幅；而且清单里的场次读者划下去还会再遇到一遍，等于白写。

推荐场次如果有标签（今日最胶着 / 今日最大逆转），标签本身就是推荐理由；没抢到标签的，卡片顶部补一行橙字「值得看 · 落后 16 分翻盘」，不然读者看不出它凭什么排前面。

准入是硬门槛，**占一条才收**，全占不上就不进推荐区（全部不够格时推荐区整块不出现，直接「其余 N 场」）：

| 门槛 | 说明 |
|---|---|
| 绝杀 / 准绝杀 | 最后 24 秒内投进反超球 |
| 加时 | 打了几个加时都算 |
| 落后 ≥ 12 分翻盘 | 胜方一度落后两位数 |
| 分差 ≤ 3 分 | 没有逐回合数据时只能看这个 |
| 交替领先 ≥ 12 次且分差 ≤ 8 | 真·你来我往 |
| 交替领先 ≥ 20 次、末节胶着 ≥ 480 秒且分差 ≤ 12 | 互咬到最后一节、末段才被拉开 |

最后一条是给「最后才拉开」开的口子。11-04 森林狼 117-107 火箭：交替领先 26 次、打平 15 次都是全天最高，末节 647 秒里分差没超过 5 分，10 分是最后阶段才拉开的，原先被「分差 ≤ 8」一刀切掉。这里的「末节胶着」指**第四节及加时内分差 ≤ 5 分的净时长**（一节 720 秒，480 秒即三分之二节）。必须同时满足交替 ≥ 20 和末节胶着，所以它**不是**把「末节贴着打」这条独立门槛放回来。

**故意不收「末节贴着打」**。4 分球但整节谁也没真追上，理由写完是「末节大半节贴着打」，读者看完提不起兴趣，列出来只是凑数。11-02 老鹰 108-104 步行者就是这类：交替领先只有 4 次、末节胶着 265 秒，新规则下依然不收；同日国王 115-100 独行侠交替 17 次但末节胶着 0 秒、赢 15 分，也不收。

**不收上限**。够格的几场就排几场，不为凑数砍到三场——好球多的日子砍掉一场都是浪费。`WATCH_MAX = 10` 只是安全阀，防的是收官日 30 队同天、万一半数都够格时推荐区把整页占满。

### 比赛评级：从「夯」到「拉完了」

每场卡片顶部第一个徽章是评级，六档从热到冷：**夯 → 顶级 → 人上人 → NPC → 拉 → 拉完了**。被折叠成一行比分的场次也带评级。**页面不放规则图例，页脚也不写评级口径**：徽章本身是玩梗词＋配色，读者不需要先看一行说明才能读，完整规则只写在本文件里。

评级是**绝对标准，不是当天排名**：可以一整天全是「夯」，也可以一场「拉完了」都没有，不为凑齐梯度硬贴。逐回合数据缺失时只按分差给中间档，不评「夯」也不评「拉完了」。判定在 `rate_game()` 里从高到低命中即停：

| 档 | 命中条件 | 典型理由 |
|---|---|---|
| 夯 | **先过推荐准入，且最终分差 ≤8（结局没打花）**，再占一条：压哨绝杀 / 最后 24 秒反超 / 加时 / 落后 ≥12 分翻盘 / 末节胶着 ≥360 秒 / 末节胶着 ≥240 秒且交替领先 ≥10 次 | 落后 14 分翻盘，最后只差 6 分；末节咬了 8 分钟，最后只差 6 分 |
| 顶级 | 达到「推荐比赛」任一准入，但没占上面的极致瞬间；**或结局拉开到两位数**（逆转再大、末节咬过也只到这里） | 落后 15 分翻盘，但最后拉开到 14 分 |
| 人上人 | 没够到推荐线但有内容：从落后 ≥8 分打回来、分差 ≤8 且激烈度 ≥25、末节胶着 ≥240 秒、交替 ≥10 次、激烈度 ≥70。**末节没缠斗又拉开两位数的不给这档** | 只差 7 分、末节咬了 10 分钟 |
| NPC | 兜底：不好不坏；小分差但全程没缠斗的也落这里 | 只差 8 分，但全程没缠斗 |
| 拉 | 赢 ≥10 分且末节胶着 ≤60 秒；或赢 ≥12 分且胶着 ≤120 秒；或赢 ≥15 分且胶着 ≤180 秒 | 赢 12 分，末节没缠斗 |
| 拉完了 | 赢 ≥20 分、末节胶着 ≤60 秒、交替 ≤6 次、激烈度 <45；或赢 ≥25 分且胶着 ≤30 秒 | 赢 39 分，全程没缠斗 |

**和推荐区对齐**：「夯 + 顶级」直接复用 `watch_ok()` 那套准入 —— 先过准入，再在好看的场次里挑出「夯」，所以不会出现「评成夯却没进推荐」。反过来说，推荐区 = 导语那场 + 夯/顶级；导语那场即使当天整体平淡（例如 11-05 只有 2 场）也固定排第一，评级可能只是「人上人」，这是有意的，不为了版面给平淡场抬评级。

**结局与末节是分水岭（2026-11-07 定）**：评级不只看「过程曾经多刺激」，还看**最后是不是还咬着**。「夯」统一要求最终分差 ≤8，逆转让再大、末节咬过再久，收尾拉开两位数也只到「顶级」，理由里写明「但最后拉开到 N 分」。11-06 的三场正好是分界线：猛龙 121-107 雄鹿落后 15 分翻盘、末节咬过 384 秒，最后却赢 14 分 → 顶级；森林狼 115-109 鹈鹕末节咬了 473 秒、最后只差 6 分 → 夯；开拓者 118-124 湖人两位数逆转、最后只差 6 分 → 夯。

原来的「落后 ≥15 分翻盘」不再单独定夯，「分差 ≤5 且激烈度 ≥150」那条也删了 —— 激烈度这个量纲下常规比赛只有 50–80，150 几乎永不触发，等于把「过程最胶着」这条路堵死了。现在改用可复核的末节实据：胶着 ≥360 秒，或胶着 ≥240 秒且交替 ≥10 次。中段来回十几次、末节胶着 0 秒又拉开两位数的（11-06 爵士 100-112 独行侠、马刺 124-109 国王）从「人上人」降到「拉」。

「拉完了」和「末节打花的拉」判定都放在「人上人」**前面**，一场球只要真有过胶着，就不往「拉」里扔。`comeback` 是**胜方曾经落后多少**，理由写成「从落后 N 分打回来」，别写成输方追分。

`latest.json` 里每场多一个 `rating`（`key` / `name` / `reason`），顶层另有 `rating_scale` 和 `rating_counts`，发布台和后续选题可以直接读。

### 今日炸裂：固定名单之外的临时入选

`focus.json` 里的六个人是**固定追踪名单**，每天都要列，跟表现好坏无关 —— 0 分 0 板 0 助也照列，缺阵写「未出场」。这一条不能被下面的门槛改写：临时入选只**加人**，不删人、不按数据过滤名单。

焦点球星区下方挂一个「今日炸裂」子块，收的是**不在固定名单里**、当天打出稀罕数据的人。硬门槛，占一条就上，一条都没占就整块不写（不保底、不凑数）：

| 门槛 | 徽章文案 |
|---|---|
| 得分 ≥ 50 | 砍下 52 分 |
| 单节得分 ≥ 20 | 单节 22 分 |
| 三双（得分 / 篮板 / 助攻各 ≥ 10） | 三双 22分 12板 11助 |
| 40 ≤ 得分 < 50 | 轰下 43 分 |
| 三分命中 ≥ 8 | 9 记三分 |
| 篮板 ≥ 20 / 助攻 ≥ 18 | 21 个篮板 / 19 次助攻 |
| 抢断 ≥ 6 / 盖帽 ≥ 6 | 6 次抢断 / 6 记盖帽 |

一人最多带两条理由，按上表顺序取最稀罕的。`BREAKOUT_MAX = 6` 只是收官日 30 队同天时的安全阀。

**单节得分**是 ESPN `plays` 逐回合累加出来的（boxscore 只有全场数据）：每个 `scoringPlay` 的 `scoreValue` 按 `period` 归到 `participants[0]` 名下。这里有一道自校验 —— **play 累加总分必须和 boxscore 的 `PTS` 完全相等，否则这个球员的单节数据一律不采信**。宁可漏报，也不能把解析错误写成「单节 22 分」发出去。逐回合数据缺失时，其余门槛照常判，只是不评单节。

固定名单里的人当天也达标时，**原地加一个橙色徽章**，不重复列进子块。`latest.json` 顶层多了 `breakouts`，`focus` 每行多了 `reason`。

**其余场次里一定标一场「今日最平淡」。** 判定条件偏严（分差上双 + 末节几乎没缠斗），有些日子一场都挑不出来，那样读者就完全看不出哪场可以跳过。所以加了兜底：标签没分出去时，从其余场次里取激烈度最低、分差 ≥ 8 的那场标上。这是有意为之——推荐区告诉你哪场值得看，这一行告诉你哪场可以不看。

**交替领先那条为什么配对分差上限**：15 分差的比赛也能算出「交替领先 17 次」，因为前三节咬、末节拉开。只写次数不写分差，读者会以为要看一场到最后一秒的球，点进去发现输了 15 分，等于骗点击。

理由只讲最抓人的那一件，按信息量排：压哨绝杀 → 最后 N 秒反超 → 加时 → 落后 N 分翻盘 → 最后两分钟没超过一个球 → 交替领先 N 次 → 只差 N 分。

**明日焦点**在文末：拉比赛日次日的赛程，挑一场推荐，再把**勇士 / 湖人 / 76人 / 火箭 / 马刺**这五队的其他场次一并列出（主推那场不重复）。没有比赛的日子会写清原因和下一个比赛日。判断依据是可复核的数据 —— 两队战绩、是否全美直播、是不是 NBA 杯、有没有焦点球星出战。休战的「原因」只从 `idle_notes.json` 里读，没登记过的日子只写「联盟当天没有排赛」，**不猜**，猜错比不写更伤信任。

流量队名单在 `fetch_nba.py` 顶部的 `CORE_TEAMS`（只影响排序优先级）；实际会列出来的队，是 `focus.json` 里出现过的所有队，所以往 `focus.json` 加人，那支队就会自动进预告。

**今日最佳一球**：全天挑一个最炸的动作，**挂在那场比赛自己的卡片底部**，不在文末单开一块（那个位置留给广告）。候选是空接、扣篮、28 英尺外三分、第四节盖帽，有绝杀时绝杀无条件胜出。分数低于 45 分就不写 —— 宁可不写，也不拿第三节的普通扣篮充数。

> 注意：这**不是**「NBA 官方十佳球」。官方那份榜单是 NBA 自家账号每天发的一条视频，没有逐场归属的公开接口（ESPN 的 `summary.videos` 该场是空数组），所以这里是自己按动作类型和时间点挑的。页面上不会写「十佳球」三个字，避免被读者当成官方口径。

**加时赛**：单节比分表会在第 5 列起标 `OT` / `OT2` / `OT3`，不限个数；下方另起一行「加时赛 / 经过 N 个加时」；走势图横轴自然延长；绝杀判定会把加时算进去，徽章显示为「加时绝杀」。

**季后赛系列赛比分**：比分正下方一行橙字，例如「尼克斯 3-1 领先 · 手握赛点」「系列赛 3-3 打平」「凯尔特人 4-2 晋级」。
数据取自 `summary.header.competitions[0].series`，但只认 `type=playoff` 的那组 —— 常规赛也会返回一组 `series`，那是「赛季系列赛」（同两队 4 次交手的战绩），拿来显示会把读者绕晕。
另外**不要**去翻译 `summary` 那句英文（`"NO leads series 1-0"` 里是 ESPN 的队名缩写，和我们中文队名对不上），用 `competitors[].wins` 配 team id 自己拼才准。
季后赛里卡片底部的「尼克斯 2-1 ｜ 凯尔特人 1-2」会自动隐藏，因为那就是系列赛战绩，和上面重复。

**明日焦点在季后赛会换口径**：常规赛用「两队战绩咬在一起（6胜1负 / 5胜1负）」当推荐理由，季后赛这条没意义，改成系列赛大比分（「尼克斯 3-1 领先，赢下就晋级」）；场次措辞也从「那天全联盟 14 场」变成「那天 4 场季后赛」。

**一天最多详写 15 场**（`MAX_DETAIL`）。常规赛收官日会让 30 队同天打完，超过 15 场时**先保证推荐场都在**，剩下的名额按开球时间给其余场次，多出来的压成「另外 N 场」的一行比分。早先的版本是按激烈度砍，那样会出现「推荐区推了某场、正文里却找不到这场」的矛盾。

**封面图**：每次生成 `docs/cover.png`（900×383，公众号头条 2.35:1）。浅色底（白 → 极浅灰）+ 当日主打那场的大比分 + 上下两条两队拼色带。左上角橙底白字是品牌位「去球吧」，紧跟一行灰色小字「NBA 每日战报」——只写品牌，划过信息流的人看不出这是篮球号；只写品类，又白占一块最显眼的位置。两者宽度不够并排时，脚本会把品类小字整个丢掉，绝不叠在日期上。
底色刻意用浅色不压深——公众号信息流本身是白底，深色封面像贴了块补丁，缩成小图时反而糊。
配色取自 ESPN 的 `team.color`，**不用任何 NBA 照片或球队 logo** —— 单色和排版不受版权保护，比赛图和 logo 是另一回事。
中文靠 `fonts-wqy-zenhei`（文泉驿正黑，可商用），不能用 Windows 的微软雅黑（微软版权，也装不到 Ubuntu 上）。没装 Pillow 或找不到字体时只打一行警告，不影响出稿。

**走势图**：每场一张「比分随时间」的双折线，砖红为主队、蓝为客队，两条线的间距就是分差、交叉就是反超。图是用 `chart.py` 手写像素直接生成 PNG 的，**没有引入 matplotlib**——一是 Actions 不用多装东西，二是 CI 里没有中文字体，图上加字只会是方块，所以队名和配色说明放在图片外的 HTML 里。

光靠图下方那行小图例，读者看图时已经滑过去了，所以**卡片顶部的大比分直接染成对应的线色**：左边客队蓝、右边主队砖红，看到比分就完成了一次配色对照。这里颜色只负责「哪条线是哪队」，**谁赢仍由队名的深浅和字重表达**（胜方深色加粗、负方灰色），别把两个信息挤到同一个视觉维度上，否则一染色就读不出胜负了。

**今日主打**：每次另外生成 `docs/feature.md`，从当天全部比赛里只挑**一场**，同时服务公众号次条和头条号。

为什么只挑一场：公众号主条已经是 15 场全展开，次条再全展开就是自己跟自己重复；头条更严格，平台运营规则里明确把「批量发布同质化内容、模板化内容无个人观点」列为降权项，同一套战报换个数据发过去，在公众号是专业感，在头条就是低质重复。

**怎么挑**：绝杀 +100 分、加时 +35、分差 ≤3 加 45、交替领先和最大逆转各按次数加、焦点球星 30 分以上再加。分最高的那场就是主打。简报里的「今日最狠的一场」只在高分场次几乎打平时用于对齐，不会为了对齐导语错过当天唯一的绝杀。

`feature.md` 给的是一篇稿子的施工图，不是成品：

- 两组标题（头条 ≤30 字 / 公众号一组，措辞刻意错开，避免两边写得像同一篇）+ 54 字内的公众号摘要
- 一句可以直接用的开场（绝杀场从那一球切进去，逆转场先给结果）
- 分类型的四段骨架，每段写清「写什么、约多少字、别写什么」
- 全天可复核的数字，每条都能对着 ESPN 的 boxscore 验
- 末尾一张两平台差异表：字数、开头、人称、数据密度、结尾

不替你写正文 —— 正文得是你自己的话，否则又变成机器生成、又踩头条的模板化红线。

休战日不会硬凑：没比赛就只留一句提示（别发战报、改发明日预告），不会生成一篇空稿。

**为什么不用 API 自动发到头条**：头条的文章发布能力在字节开放平台，要申请创作类权限，个人号基本拿不到。网上那些「头条自动发文」都是浏览器模拟点击，而头条的风控恰好把「批量发文 + 频繁换 IP」判定为机器批量运营，封号不用人工审核。所以这一步**只能手动**，脚本只负责把素材准备好。

**每场的「数据看点」也要扫一眼。** 它是从数据里算出来的（最大领先、末节反扑、分差极值），通常是对的，但它是钩子不是结论——直接改成你自己的判断句更好用。

**球员中文名**：`scripts/players_zh.json` 现在 450 条，覆盖了 11-02 那天全部 394 名出场球员，正文里不会再冒英文姓氏。

关于「官方译名」得先说清楚：新华社译名室出的是《世界人名翻译大辞典》，那是外国人名的通用音译规范，**NBA 球员没有单独的词条库**。实际通行的写法来自央视、腾讯、新浪的日常报道，这几家之间也不完全统一——约基奇、东契奇这种没人写错，边缘球员就各写各的。所以这张表本质是「媒体通行写法表」，不是「官方标准表」。哪天看到不对的，直接改 JSON，不用管什么规范。

补的优先级：

1. 有明确共识的（约基奇、东契奇、字母哥）→ 直接写
2. 同姓球员必须用名字区分（杰伦·布朗 / 杰伦·威廉姆斯 / 杰林·威廉姆斯；米切尔 / 狄龙·米切尔 / 阿贾伊·米切尔）
3. 冷门双向球员 → 按常规音译，读着顺就行
4. 真拿不准 → **留英文姓氏，比写错强**

每场比赛正文里只出现每队得分前三，所以补表也只补到这一层就够。赛季中新秀进来、或者双向球员打出来了，跑一次：

```bash
python scripts/check_names.py            # 查昨天（按北京时间推比赛日）
python scripts/check_names.py 2026-11-02 # 查指定比赛日
python scripts/check_names.py --all      # 连替补一起查
```

它把缺的人列出来，并打印一份已经填好 key 的 JSON 模板，填上中文名粘回 `players_zh.json` 就行。**不自动翻译**——机翻会把「约基奇」写成「乔基奇」。

## 可调项

**改触发时间**：编辑 `.github/workflows/daily-report.yml` 里的 cron。注意 **cron 是 UTC 时间**，北京时间减 8 小时。北京 15:23 → `23 7 * * *`，北京 14:07 → `7 6 * * *`。分钟数建议避开 :00 / :30，减少和 GitHub 高峰排队撞车导致漏投。

**补跑某一天**：Actions → Run workflow，在 `game_date` 里填 `2026-11-01` 这种格式（**美国比赛日**）。

**补球员中文名**：往 `scripts/players_zh.json` 里加 `"英文全名": "中文名"`。查不到的会回落成英文姓氏（如 `Traore 16分2板6助`），不影响出稿。

**改焦点球星**：编辑 `scripts/focus.json`，每项三个字段 —— `en`（ESPN 里的英文全名，必须完全一致）、`cn`（中文名）、`team`（所属球队英文全名，用于判断「球队打了但人没上」）。

这一块是**固定追踪名单，不是当日评选榜**。名单上的人每天都要出现，读者看的是「我今天关注的这几个人怎么了」，跟打得好不好无关：上场但 0 分 0 板 0 助照列，缺阵写「未出场」，球队没比赛写「今日无赛事」。**不要加按数据过滤的逻辑**（只留得分高的、数据全 0 就跳过），那会把它改成另一个当日最佳榜。

当前名单：库里、东契奇、詹姆斯、杜兰特、文班亚马、杨瀚森。杨瀚森在 ESPN 里写作 **`Yang Hansen`**（姓在前），别写成 `Hansen Yang`。

每天自动判断三种情况：**上场了给数据，球队打了但人没上标「（未出场）」，球队当天没比赛就整条不出现**。所以这份名单不需要每天维护。

注意 `team` 要跟着交易走。写错了会怎样：如果球员当天其实上了场，脚本以当天名单为准，会照常显示正确球队；只有「他所在的新队当天没比赛、旧队有比赛」时才会误标成旧队，这时他会顶着旧队名显示「（未出场）」。所以每次大交易后顺手改一下即可。

## 排错

**拉不到比赛 / 数量是 0**
NBA 不是每天都有比赛（全明星周末、感恩节、圣诞前一天都可能是空场）。脚本会生成一张「今天没有比赛」的占位页，属正常。先确认那天是否真的有比赛。

**显示「尚未结束」/ 页面停在上一期**
四档定时任务在出稿前都会查一次 ESPN：比赛日只要还有一场没终场，就整档跳过、不碰 `docs/`，线上保留上一期完整战报。这样既不会推少了几场的残缺版，也挡住了另一种情况：GitHub 把晚间档延迟到次日凌晨才投递，那时当天比赛一场都还没开打，脚本会把它们全排除、推一份 0 场空战报上线。等下一档比赛全部终场后自动出稿；几档都没赶上就手动跑一次。日志打印「整档跳过，页面保留上一期战报」属正常。

**ESPN 接口变了 / 返回空**
先看 Actions 日志里有没有 `ESPN 记分板失败`。脚本会自动退回 balldontlie（需配 `BALLDONTLIE_API_KEY`），但只出比分，没有单节和球员数据。

**定时任务没按时跑**
GitHub Actions 的定时任务是「尽力而为」：通常延迟 3–15 分钟，高负载时可能延迟更久甚至**整天不投递**；新建仓库的头一两天尤其容易漏。判断方法：Actions → 该工作流 → 看有没有 `Scheduled` 标记的运行记录；一条都没有就是调度没投递，跟脚本无关（此时手动跑一次 9 步全绿，能证明脚本没问题）。补跑：Actions → Run workflow，`game_date` 留空或填美国比赛日。另外仓库连续 60 天没有提交，GitHub 会自动暂停定时任务，往默认分支推一个提交即可恢复。**注意延迟投递**：`Scheduled` 运行的创建时间可能比 cron 晚好几小时（实测当时 19:20 那档拖到次日 00:16 才跑）；此时出稿前检查会拦下它，页面保留上一期，不会推空战报。

**日志里有战报，但仓库里的 `docs/` 没更新（推送被拒）**
按可能性从高到低查三件事：

1. **仓库的 Workflow 权限是只读的**（最常见）。`Settings → Actions → General → Workflow permissions` 必须选 **Read and write permissions**。工作流里写的 `permissions: contents: write` 只能往下削，不能突破仓库这一层的上限，所以仓库设成只读时，那行写了也没用，日志会报 `403`。
2. **`main` 开了分支保护**。`Settings → Branches` 里如果给 `main` 加了规则，机器人推不进去，会报 `protected branch hook declined`。要么关掉，要么把 `nba-report-bot` 加进例外。
3. **真的撞车了**。有人在任务运行的那两分钟里在网页端改过文件，`git push` 会因 non-fast-forward 被拒。工作流本身会 `pull --rebase` 后重试三次，多数情况能自己解决；连续三次失败才会报错，这时手动 `Run workflow` 一次即可。

**走势图不显示**
图是相对路径 `charts/xxx.png`，只有在 `docs/` 目录一起提交、并且从 Pages 地址打开时才能显示。本地直接双击 `report.html` 也能看；但如果只把 html 单独拷走，图会丢。

**往公众号粘贴后图没了**
浏览器里全选复制粘贴，图片会由公众号编辑器自动上传，前提是你打开的是 **Pages 的 https 地址**，不是本地文件。从本地 `file://` 粘过去，图片可能上传失败。真出现裂图时，打开发布台第 6 节展开「全部走势图的 https 直链」，逐张下载再手动插入。

**建议先彩排一次**：用当期战报复制粘贴到编辑器、存成草稿但**不要点群发**，确认 14 张图都被微信自动上传了再走正式流程。草稿不占当天的群发额度，这一步能提前试出微信服务器能不能抓到 Pages 上的图片，避免正式发布时才发现。

**比赛日对不上**
脚本默认取「北京时间昨天」作为比赛日，因为美国晚上的比赛换算到北京时间已经是第二天。注意 ESPN 的 `dates` 参数按**美国东部日期**算，与「美国比赛日」一致。
